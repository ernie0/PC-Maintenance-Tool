要做：
- 協助：員工求助，資訊人員連過去操作。

- Wake-on-LAN：由 NAS 在辦公室區網送出喚醒封包。

- 離線告警（Telegram）。

- 隱藏模式：被監看或被操作時一定有提示。
- 遠端命令列（第一版）。
- 自動散播或自動安裝到其他電腦。
- 連到第三方的公用中繼網路。

## 4. 架構

```
                    ┌──────── NAS（Docker）─────────┐
[控制端 Viewer] ──┬─▶│ PcRemote.Server ◀── cloudflared │◀── 外部：https://（Cloudflare）
（電腦維護工具）   │  │ 帳號、電腦清單、配對、中繼       │
                  │  └───────────────▲──────────────┘
   辦公室內：直接連 NAS 的區網位址      │ WSS（只轉送加密過的資料）
                                    │
                   [被控端 Agent 服務 ＋ Session 程式]（員工電腦、工地電腦）
```

- **連線路徑。** 被控端和控制端都設定兩個伺服器位址：NAS 的區網位址和外部網址。先試區網，連不上再改走 Cloudflare。辦公室內的畫面流量不會經過 Cloudflare。
- **cloudflared。** 跟伺服器放在同一份 compose，只對外提供 HTTPS／WSS。NAS 不開任何 port。
- **WebSocket 斷線。** Cloudflare 會不定時切斷長時間連線，所以每 15 秒送一次心跳；斷線後依 1、2、4… 秒、最多 30 秒的間隔自動重連，重連後恢復原本的連線。
- **直連（P5）。** 同一個區網，或打洞成功時直接連線，可以再省頻寬和延遲。第一版不做。

## 6. 連線模式

| 模式 | 用途 | 對方要按允許？ | 被控端提示 |
|---|---|---|---|
| 協助 | 員工求助 | 要。或由員工報出一次性密碼 | 紅框＋浮動列「○○ 正在操作這台電腦」＋「中斷」鈕 |
| 管理 | 工地電腦、下班後維護 | 不用。需要管理者先對這台電腦開啟，並有權限 | 同上 |
| 監看 | 員工電腦、工地電腦，只看不操作 | 依公司設定，預設不用 | 系統匣圖示變色＋浮動列「畫面正在被檢視」，不能關閉 |
| 電腦牆 | 一次看多台 | 同監看 | 同監看 |

### 6.1 配對與隱藏模式（2026-11-22 使用者決定）

- **配對：** 第一次連線時，被控端顯示提示，由被控端的人按「同意」，控制端也確認六位數驗證碼相符（雙方都同意）。配對成功後，被控端把這個控制端（管理者憑證的公鑰指紋）記成已授權。
- **隱藏模式：** 配對完成後，該控制端之後再連這台，可以要求進入隱藏模式——被控端不再跳提示、也不顯示連線中的提示列。只有「已配對」且控制端送出 `RequestHidden` 時才會進入；沒配對過的控制端，這個旗標會被忽略，一律照正常流程顯示提示並要求同意。
- **這取代了原本「監看一定有提示、不做隱藏模式」的設計。** 依使用者 2026-11-22 的決定。
- **隱藏模式在被控端完全不留痕跡（2026-11-22 使用者決定）：** 不跳提示、不顯示提示列、連系統匣圖示都不顯示。
- **仍保留的兩點（不是螢幕上的痕跡，不違反「不留痕跡」）：** (1) 伺服器端的連線稽核紀錄照記（誰、何時、哪台、多久），供公司／管理者查核，被控端畫面上看不到；(2) 配對狀態可在電腦維護工具主程式的「遠端協助」設定頁解除（不是靠匣圖示）。若這兩點也要拿掉再告訴我。

## 7. 安全設計

- **公司根金鑰。** 由使用者離線保管，用來簽發「管理者憑證」。憑證內容是管理者公鑰、權限（可以協助／管理／監看哪些群組）和到期日。
- **被控端只信根金鑰。** 安裝時寫入公司根公鑰，只接受由有效管理者憑證簽署的連線要求。這樣伺服器被攻破也無法偽造連線。
- **端對端加密。** 每次連線由控制端與被控端用 ECDH P-256 交換金鑰，雙方各自簽章，之後所有資料用 AES-GCM 加密。伺服器只看得到密文。
- **稽核紀錄。** 伺服器和被控端各記一份：誰、何時、哪台、哪種模式、多久、傳了哪些檔案。被控端那份伺服器改不到。
- **伺服器登入。** 帳號加 TOTP 兩步驟驗證。登入嘗試有次數限制。
- **權限。** 依群組分別授權協助、管理、監看。無人值守預設關閉，要逐台開啟。
- **提示。** 預設一定有提示。例外是已配對的控制端進隱藏模式（見 6.1）；隱藏連線仍寫進稽核紀錄。
- **知識庫。** 不記錄連線網址、帳密和金鑰。

## 8. 被控端技術

- **擷取：** DXGI Desktop Duplication，只處理有變動的畫面。螢幕切換、解析度改變（ACCESS_LOST）時自動重建。支援多螢幕。
- **色彩轉換：** 用 GPU（D3D11 Video Processor）把 BGRA 轉成 NV12。P0 驗證程式用的是 CPU。
- **編碼：** Media Foundation H.264，硬體優先，失敗自動退回軟體。每台電腦第一次啟動時做 2 秒自我測試，選出可用的編碼器。依網速調整位元率和幀率，畫面沒變化就不送。
  - 注意：雙顯示卡的電腦，擷取和編碼要在同一張卡上，否則要跨卡複製。
- **輸入：** SendInput（滑鼠絕對座標、鍵盤掃描碼）。Ctrl+Alt+Del 用 SendSAS，安裝時要設定 SoftwareSASGeneration 原則。
- **登入畫面與 UAC：** 服務以系統身分，在目前的工作階段的 `winsta0\winlogon` 桌面啟動 Session 程式。這是最容易出問題的部分，P2 要留足時間。

## 9. 控制端技術

- **解碼：** Media Foundation H.264，用 DXVA 硬體解碼。
- **顯示：** D3D11 swap chain 嵌入 WPF（HwndHost），壓低延遲。
- **鍵盤：** 用低階鍵盤攔截，連線視窗在前景時，Win 鍵、Alt+Tab 送到遠端。這是 Windows 程式比瀏覽器好的地方。
- **畫面：** 電腦清單（線上狀態、群組、最近連線、我的最愛）、連線視窗（多螢幕切換、畫質、傳檔、剪貼簿、Ctrl+Alt+Del）、電腦牆、連線紀錄、管理。

## 10. 協定草案

- **控制訊息：** WSS 文字框，JSON。種類：
  - register、heartbeat
  - session-request（含管理者憑證與簽章）、session-accept、session-reject
  - key-exchange
  - quality-report、session-end
- **影像與資料：** WSS 二進位框。格式為「1 byte 類型 ＋ 連線序號 ＋ AES-GCM 密文」。種類：video-frame、input-event、clipboard、file-chunk、cursor。
- **電腦牆：** 每台約 1 fps 的低畫質縮圖，點進去才開高畫質。

## 12. P0 驗證紀錄

### (a) 編碼器能力（2026-11-22，本機驗證）

ffmpeg 8.1.1，合成 1080p 測試畫面，30 fps，10 秒共 300 張，目標 3 Mbps。

| 編碼器 | 花費時間 | CPU 時間 |
|---|---|---|
| Media Foundation 硬體（自動選到 NVIDIA H.264 Encoder MFT） | 0.97 s | 0.83 s |
| Intel QSV（ffmpeg `h264_qsv`，透過 oneVPL） | 1.80 s | 1.42 s |
| NVENC（直接呼叫） | 0.61 s | 0.58 s |
| x264 ultrafast | 0.34 s | 2.30 s |
| Media Foundation 軟體（H264 Encoder MFT） | 0.70 s | 4.23 s |

### (b) .NET 擷取→編碼→解碼（2026-11-22，本機驗證）

- **程式：** `spikes/p0-pipeline`（Vortice 3.8.3）。
- **流程：** Desktop Duplication → CPU 轉 NV12 → Media Foundation 編碼 → Microsoft 軟體解碼，同一台電腦、不經網路。
- **測試條件：** 1920×1080，30 fps，每段 10 秒，目標 4 Mbps。
- **兩種畫面：** 「一般操作」是桌面加一個移動方塊；「整頁捲動」是整個畫面每張都在變。
- **隱私：** 畫面只在記憶體，不存檔，只輸出數字。
- **測了兩輪：** 第一輪事件不指定 D3D，第二輪指定 D3D。測試期間使用者正在用這台電腦，所以桌面變化量每次不同。

| 情境 | 編碼器 | 合計延遲 平均／P95（ms） | 其中編碼（ms） | 位元率 | PSNR(Y) | 程式 CPU（單核％） |
|---|---|---|---|---|---|---|
| 一般操作 | NVIDIA 硬體 | 8.8～13.4／14.4～22.0 | 3.0～5.1 | 2.2～3.1 Mbps | 47.6～50.5 dB | 29～60 |
| 一般操作 | Microsoft 軟體 | 13.1～13.5／18.3～21.4 | 3.9～4.1 | 3.7～4.0 Mbps | 40.9～46.3 dB | 53～94 |
| 整頁捲動 | NVIDIA 硬體 | 13.0～13.9／20.9～26.8 | 4.7～5.5 | 3.4～3.9 Mbps | 47.0～50.0 dB | 37～46 |
| 整頁捲動 | Microsoft 軟體 | 15.1～15.6／21.9～22.6 | 4.0～4.2 | 4.2～4.3 Mbps | 40.5～43.6 dB | 64～65 |

結論：
- **本機延遲不是瓶頸。** 本機管線的合計延遲平均 9～16 ms、P95 14～27 ms，最大值 25～73 ms，遠低於區網 100 ms 的目標。延遲主要會來自網路，下一步要驗證 Cloudflare Tunnel 和 4G。
- **CPU 佔用。** 這台電腦是 32 執行緒，換算全機只佔 0.9～2.9%。這個數字還包含 CPU 色彩轉換和軟體解碼；正式版色彩轉換改用 GPU，解碼在控制端，所以被控端會更低。一般辦公室 i5 電腦還沒量。
- **NVIDIA 硬體編碼可用。** 透過 Media Foundation 呼叫正常。
- **Intel 內顯（Media Foundation）在這台失敗。**
  - 設低延遲時，送 1 張就沒有回應。
  - 不設低延遲時，收了 17 張都沒有輸出。
  - 有沒有指定 Intel 的 D3D11 裝置都一樣。
  - 這台的 Intel 內顯沒有接螢幕，ffmpeg 透過 oneVPL 的 `h264_qsv` 正常，所以問題出在 Media Foundation 的 Intel 編碼器。
  - 要拿「內顯直接接螢幕」的辦公室電腦實測。實機也不行就改用 oneVPL，或退回軟體編碼。
- **重跑方式：** 在 `spikes/p0-pipeline` 執行 `dotnet run -c Release`。可用環境變數：`P0_ONLY=名稱` 只跑某個編碼器，`P0_SECONDS=秒數`，`P0_NOLOWLAT=1` 不設低延遲。

### (c)～(e) 還沒做

- **(c) Cloudflare Tunnel：** 使用者 2026-11-22 決定先不測。之後要測時，在 NAS 或這台跑 cloudflared，量延遲、頻寬和多久斷一次；也要確認 Cloudflare 服務條款對大量影像流量的限制。
- **(d) 工地 4G 實測：** 要到現場。
- **(e) 一般辦公室電腦：** 要拿一台只有 Intel 內顯的電腦實測。

## 13. 風險

1. **防毒誤判與 SmartScreen：**
   - 使用者決定先不買憑證、接受誤判。
   - 因應做法見第 2 節。
   - 公開安裝檔多了遠端元件，整個電腦維護工具的下載信譽也可能受影響。
2. **登入畫面與 UAC 的桌面切換：** 最容易出問題。
3. **Intel 內顯編碼：** 見第 12 節 (b)。
4. **Cloudflare：** 長連線會被不定時切斷，服務條款對影像流量也可能有限制。設計上中繼端點要可以替換。
5. **4G 流量：** 一路估計 0.5～4 Mbps；電腦牆每台約 50～150 kbps（估計）。
6. **法規：** 員工監看需要公司規章與事先告知。
